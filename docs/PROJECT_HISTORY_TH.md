# ประวัติการพัฒนา Phish Radar AI Extension Demo (เดิม v1.0)

> เอกสารนี้เก็บไว้เป็นประวัติ บางหัวข้ออ้างถึงหน้าเดโมหรือไฟล์ทดลองที่ไม่ได้อยู่ใน runtime v2.0 แล้ว วิธีใช้งานปัจจุบันให้ยึด README.md ที่ root เป็นหลัก

เดโมนี้เป็น **Chrome Extension สำหรับคัดกรองเว็บไซต์ Phishing ก่อนเข้าถึง** โดยใช้แนวคิด **AI-Lite / Explainable Rule-Based Scoring** เพื่อสาธิตโปรเจคสัมมนา/โปรเจควิชา

> หมายเหตุ: ตัวนี้เป็นเดโมเพื่อการศึกษา ยังไม่ใช่ระบบ production และยังไม่ได้ใช้โมเดล AI ที่ train จาก dataset จริง

## จุดขายสำหรับนำเสนออาจารย์

โปรเจคนี้ไม่ได้รอให้ผู้ใช้เข้าเว็บ phishing แล้วค่อยเตือน แต่ทำเป็นหลายด่าน:

1. สแกนลิงก์บนหน้าเว็บก่อนคลิก
2. ดักคลิกลิงก์เสี่ยงก่อนเปิดปลายทางจริง
3. Redirect ไปหน้า Warning หาก URL มีคะแนนเสี่ยงสูง
4. ตรวจหน้าเว็บที่มีช่อง password / OTP แล้วเตือนก่อนผู้ใช้กรอกข้อมูล
5. แสดงเหตุผลเป็นข้อ ๆ ว่าทำไมถึงเสี่ยง

## ฟีเจอร์ในเดโม

- วิเคราะห์ URL ของเว็บที่กำลังเปิด
- แสดงคะแนนความเสี่ยง 0–100 ใน popup
- แสดงเหตุผลการให้คะแนน เช่น +24 URL มี OTP/token หรือ +30 โดเมนคล้ายแบรนด์
- ไฮไลต์ลิงก์ที่น่าสงสัยในหน้าเว็บ
- มี badge HIGH/WARN ข้างลิงก์
- มี mini panel สรุปจำนวนลิงก์เสี่ยงบนหน้าเว็บ
- ดักคลิกลิงก์เสี่ยงก่อนเปิดจริง แล้วพาไปหน้า Warning
- ตรวจช่อง password / OTP / token บนหน้าเว็บ
- ตรวจ form action ว่าส่งข้อมูลไปโดเมนอื่นหรือ HTTP หรือไม่
- มีหน้า Demo Page สำหรับทดสอบโดยไม่ต้องเข้าเว็บ phishing จริง
- มีช่องทดสอบ URL เองใน popup
- ทำงานแบบ local ไม่ส่ง URL ออกนอกเครื่อง
- ถ้าเว็บ/หน้าเว็บปลอดภัย จะแสดงสัญลักษณ์ ✅ และ badge สีเขียวทั้งใน popup, toolbar badge และกล่องสถานะมุมจอ

## Rule-Based Engine ตรวจอะไรบ้าง

### 1. URL Shape

- URL ยาวผิดปกติ
- path ลึกหลายชั้น
- query parameter จำนวนมาก
- มี URL ซ้อนใน URL
- มี encoded URL เช่น `%3A%2F%2F`
- มีเครื่องหมาย `@` เพื่อหลอกปลายทางจริง
- มี backslash `\`

### 2. Domain Risk

- ไม่ใช้ HTTPS
- ใช้ IP address แทนชื่อโดเมน
- ใช้ public/private IP
- ใช้ port แปลก เช่น `:8080`
- subdomain ซ้อนหลายชั้น
- ชื่อโดเมนยาวผิดปกติ
- มีขีดกลางเยอะ เช่น `kbank-login-verify`
- มีตัวเลขเยอะ
- ชื่อโดเมนดูสุ่มจาก entropy
- ใช้ TLD ที่เสี่ยงในบริบท phishing เช่น `.top`, `.xyz`, `.click`, `.cfd`
- ใช้ free hosting / dynamic DNS เช่น `netlify.app`, `pages.dev`, `duckdns.org`

### 3. Brand Impersonation

ตรวจชื่อแบรนด์และโดเมนคล้ายแบรนด์ เช่น:

- Google / Gmail
- Facebook / Meta
- Instagram
- TikTok
- Medium
- LINE
- PayPal
- Apple / iCloud
- Microsoft / Office / Outlook
- Amazon
- Netflix
- Steam
- Discord
- Binance
- KBank / Kasikorn
- SCB
- Krungsri
- TTB
- Krungthai
- TrueMoney
- Shopee
- Lazada

ตัวอย่างที่ตรวจได้:

- `paypaI-security-login.example.com` ใช้ตัว `I` ใหญ่แทน `l`
- `kbank-login-verify.top`
- `scb-secure-helpdesk.xyz`
- `account-verify-paypal.example.net`

### 4. Homoglyph / Punycode

- ตรวจ `xn--` ที่อาจเป็น IDN/Punycode
- ใช้ skeleton normalization เช่น `0 → o`, `1/! → l`, `@ → a`, `5 → s`
- ตรวจชื่อที่คล้ายแบรนด์ด้วย Levenshtein distance

### 5. Credential / Phishing Keywords

ตรวจคำที่มักใช้หลอก เช่น:

- `login`, `signin`, `verify`, `secure`, `account`, `update`
- `password`, `otp`, `2fa`, `token`, `session`, `credential`
- `wallet`, `banking`, `payment`, `billing`, `kyc`
- `urgent`, `locked`, `suspended`, `claim`, `reward`
- คำไทย เช่น `ยืนยัน`, `บัญชี`, `รหัสผ่าน`, `OTP`, `ด่วน`

### 6. Redirect / Shortener

- ตรวจลิงก์ย่อ เช่น `bit.ly`, `tinyurl.com`, `t.co`, `rebrand.ly`
- ตรวจ query redirect เช่น `?redirect=https://evil.example`
- ตรวจ parameter เช่น `next`, `target`, `returnUrl`, `continue`

### 7. Suspicious Download

ตรวจลิงก์ดาวน์โหลดไฟล์เสี่ยง เช่น:

- `.exe`, `.scr`, `.bat`, `.cmd`, `.vbs`, `.js`, `.ps1`, `.msi`, `.apk`, `.jar`, `.lnk`
- ไฟล์บีบอัด เช่น `.zip`, `.rar`, `.7z`

### 8. Link Text Mismatch

ตรวจกรณีข้อความที่ผู้ใช้เห็นไม่ตรงกับลิงก์จริง เช่น:

```text
ข้อความที่เห็น: https://www.paypal.com/security
ปลายทางจริง: https://account-verify-paypal.example.net/login
```

### 9. Page/Form Context

ตรวจจาก DOM ของหน้าเว็บ:

- มีช่อง password หรือไม่
- มีช่อง OTP/token หรือไม่
- form action ส่งไป HTTP หรือไม่
- form action ส่งข้อมูลไปคนละโดเมนหรือไม่
- มี hidden input จำนวนมากหรือไม่
- หน้าเว็บมีข้อความเร่งเร้า เช่น “ภายใน 24 ชั่วโมง”, “บัญชีถูกระงับ”

## วิธีติดตั้งแบบ Developer Mode

1. แตกไฟล์ ZIP
2. เปิด Chrome แล้วเข้า `chrome://extensions/`
3. เปิด `Developer mode`
4. กด `Load unpacked`
5. เลือกโฟลเดอร์ `phish-radar-ai-extension`
6. กดไอคอน Extension แล้วเลือก `เปิดหน้า Demo`

## วิธีทดสอบเร็ว

### วิธีที่ 1: เปิดหน้า Demo

กดไอคอน Phish Radar AI → `เปิดหน้า Demo`

ลองกดลิงก์ตัวอย่าง เช่น:

- Homoglyph Brand
- Thai Bank Scam
- OTP Trap
- Shortener
- Link Text Mismatch
- Suspicious Download

ถ้าคะแนนสูง ระบบจะพาไปหน้า Warning ก่อนเปิดเว็บจริง

### วิธีที่ 2: ทดสอบบนเว็บทั่วไป

เปิดเว็บที่มีลิงก์หลายรายการ แล้วกดปุ่ม `สแกนลิงก์ในหน้านี้` ใน popup

ลิงก์ที่มีความเสี่ยงจะถูกไฮไลต์พร้อม badge คะแนน

### วิธีที่ 3: ทดสอบ URL เอง

กด popup → วาง URL ในช่อง `ทดสอบ URL เอง` → กด `วิเคราะห์`

## ไฟล์สำคัญ

- `manifest.json` — กำหนดค่า Chrome Extension Manifest V3
- `analyzer.js` — ตัววิเคราะห์ URL/DOM และให้คะแนนความเสี่ยง
- `content.js` — สแกนลิงก์, ดักคลิก, ตรวจฟอร์มในหน้าเว็บ
- `content.css` — badge, overlay, mini panel
- `background.js` — service worker, badge, redirect ไป warning page
- `popup.html` — หน้าต่าง popup ของ extension
- `warning.html` — หน้าเตือนก่อนเข้าเว็บเสี่ยง
- `demo-page.html` — หน้าทดสอบเดโม

## โครงสร้างการทำงาน

```text
ผู้ใช้เปิดเว็บ / คลิกลิงก์
↓
content script ตรวจ href + link text
↓
analyzer.js ให้คะแนนแบบ explainable scoring
↓
ถ้าคะแนน >= threshold
↓
background.js redirect ไป warning.html
↓
ผู้ใช้เลือกย้อนกลับ หรือเปิดต่อโดยยอมรับความเสี่ยง
```

## สิ่งที่ควรพูดตอนนำเสนอ

> ระบบนี้ยังไม่ใช้ Machine Learning แต่ใช้ Rule-Based AI-Lite เพื่อแสดงให้เห็นว่า phishing สามารถคัดกรองเบื้องต้นได้จากหลายสัญญาณร่วมกัน เช่น URL ผิดปกติ, โดเมนเลียนแบบแบรนด์, คำว่า OTP/password, การไม่ใช้ HTTPS และฟอร์มส่งข้อมูลข้ามโดเมน จุดเด่นคือทุกคะแนนอธิบายได้ จึงเหมาะกับการนำไปต่อยอดเป็น ML model หรือเชื่อม API จริงในอนาคต

## สิ่งที่ควรต่อยอดเป็นโปรเจคจริง

1. เพิ่ม ML model จริง เช่น Random Forest, XGBoost หรือ Neural Network จาก dataset phishing URL
2. เชื่อม Google Safe Browsing API หรือ VirusTotal API ผ่าน backend
3. เพิ่ม backend ด้วย FastAPI/Node.js สำหรับบันทึกประวัติและวิเคราะห์ขั้นสูง
4. ตรวจ screenshot/DOM similarity ของหน้า login กับแบรนด์จริง
5. เพิ่มระบบ whitelist/blacklist รายองค์กร
6. เพิ่ม dashboard สถิติ URL ที่ถูกบล็อก
7. เพิ่ม privacy mode เช่น hash URL ก่อนส่ง server
8. ใช้ `declarativeNetRequest` สำหรับ blocklist ที่มั่นใจในระดับ production

## ข้อจำกัดของเดโม

- เป็น heuristic scoring ไม่ใช่ AI ที่เรียนรู้จากข้อมูลจริง
- อาจมี false positive / false negative
- ไม่ตรวจอายุโดเมนจริง เพราะยังไม่ได้เชื่อม WHOIS/RDAP API
- ไม่ตรวจฐานข้อมูลภัยคุกคามจริง เพราะยังไม่เชื่อม Safe Browsing/VirusTotal
- การ redirect ด้วย `webNavigation` เป็นการสาธิต pre-access protection แต่ไม่ใช่ synchronous blocking ทุก request
- สำหรับ production ควรใช้ backend + threat intelligence + ML model + allowlist ที่ดูแลจริง

## อัปเดต v0.3 — แก้ปัญหา false positive บนหน้า Google Search

จากการทดสอบบนหน้าค้นหา พบว่าเว็บค้นหาอย่าง Google อาจมีลิงก์แบบ redirect/tracking และข้อความ snippet ยาว ทำให้ rule-based engine เข้าใจผิดว่า URL ยาวหรือข้อความลิงก์ไม่ตรงปลายทาง เวอร์ชันนี้จึงปรับดังนี้:

- แกะ redirect URL เช่น `google.com/url?q=...` แล้ววิเคราะห์ปลายทางจริงแทน URL ของ Google
- เพิ่ม Search Page Mode: บนหน้าค้นหาจะแสดง badge เฉพาะลิงก์ที่มั่นใจว่าเสี่ยงสูง
- ไม่เอาข้อความ snippet ยาว ๆ ของผลการค้นหาไปคิดเป็น link text mismatch
- เปลี่ยน UI จากกรอบเส้นประใหญ่เป็น underline/badge ขนาดเล็ก เพื่อไม่ทำให้หน้าเว็บพัง
- เพิ่มจำนวน `shown` ใน popup เพื่อแยกว่า “พบลิงก์น่าสงสัย” กับ “แสดงเตือนบนหน้า”

## เว็บจำลองที่ระบบตรวจจับได้

เวอร์ชันนี้เพิ่มหน้า `simulator.html` สำหรับนำเสนออาจารย์ โดยรวมเคสตัวอย่าง เช่น โดเมนคล้ายแบรนด์, ไม่ใช้ HTTPS, URL ยาว, IP address, ลิงก์ย่อ, redirect parameter, Punycode, ไฟล์ `.exe`, URL ที่มี `@`, และฟอร์มหลอกกรอก Password/OTP

เปิดผ่าน popup ด้วยปุ่ม **เปิดเว็บจำลอง** หรือเปิดจาก `chrome-extension://.../simulator.html`

ถ้าต้องการทดสอบแบบ local file ให้เปิดไฟล์ในโฟลเดอร์ `test-sites` แล้วไปที่ `chrome://extensions` หรือ `brave://extensions` > Details ของ Phish Radar AI > เปิด **Allow access to file URLs** จากนั้น reload หน้าเว็บจำลอง

## อัปเดต v1.1: ตรวจ SEO Spam / เว็บถูกฝังไฟล์แปลกปลอมในหน้าค้นหา

เพิ่มกฎสำหรับกรณีผลค้นหา Google/Brave ที่มีหัวข้อ adult/spam แต่ปลายทางเป็นโดเมนองค์กร/การศึกษา/เว็บทั่วไป เช่น path แบบ `wp-content`, `wpforms/tmp`, `wpcf7-files`, หรือไฟล์ PDF ที่ไม่สอดคล้องกับโดเมนจริง ระบบจะจัดเป็น “ลิงก์เสี่ยง/SEO spam” ไม่ได้สรุปว่าเป็น phishing เสมอไป แต่ควรเตือนผู้ใช้ก่อนกดเข้าเว็บ

## อัปเดต v1.2: ตรวจเนื้อหาเสี่ยงเพิ่มเติม

เวอร์ชันนี้ไม่ได้ตรวจเฉพาะ phishing แล้ว แต่เพิ่มกฎสำหรับตรวจกลุ่มความเสี่ยงอื่น ๆ แบบ rule-based ได้แก่

- **Phishing / ขโมยข้อมูล**: โดเมนเลียนแบบแบรนด์, login/verify/OTP, ฟอร์มรหัสผ่าน
- **Malware / ไฟล์เสี่ยง**: ไฟล์ `.exe`, `.apk`, คำว่า crack, keygen, fake update, download player
- **Scam / Fraud**: ลงทุนกำไรสูง, airdrop, claim reward, free money, กู้เงินด่วน, รับประกันกำไร
- **Gambling Content**: สล็อต, คาสิโน, พนัน, เครดิตฟรี, betting/casino
- **SEO Spam / เนื้อหาอ่อนไหว**: ผลค้นหาที่ชื่อเรื่องไม่สอดคล้องกับโดเมน เช่น เว็บองค์กร/การศึกษาแต่ path เป็น PDF หรือ adult spam
- **Redirect / ปลายทางไม่ชัดเจน**: shortener, redirect parameter, URL ซ้อนใน query

เกณฑ์คะแนนที่ใช้ใน v1.2:

| คะแนน | สถานะ | ความหมาย |
|---:|---|---|
| 0–30 | ✅ ปลอดภัย | ไม่พบสัญญาณเสี่ยงสำคัญจาก rule ปัจจุบัน |
| 31–60 | ⚠️ น่าสงสัย | พบสัญญาณบางอย่าง ควรตรวจสอบก่อนเปิดต่อ |
| 61–80 | ⛔ เสี่ยงสูง | พบหลายสัญญาณร่วมกัน ควรเปิดหน้า Warning ก่อนเข้าเว็บ |
| 81–100 | 🚫 อันตรายมาก | พบสัญญาณรุนแรง เช่น malware/scam/phishing ชัดเจน |

หมายเหตุ: ระบบนี้ยังเป็น Prototype สำหรับสาธิต ไม่ใช่ระบบตัดสินความผิดกฎหมายของเนื้อหา และยังไม่เชื่อมฐานข้อมูลภัยคุกคามจริงภายนอก
