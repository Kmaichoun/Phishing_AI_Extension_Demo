# สคริปต์นำเสนอ Phish Radar AI-Lite Extension

## ชื่อโปรเจค

**Phish Radar AI-Lite: Chrome Extension สำหรับคัดกรองเว็บไซต์ Phishing ก่อนเข้าถึง โดยไม่ใช้ ML Model**

## ปัญหา

ผู้ใช้จำนวนมากถูกหลอกให้คลิกลิงก์ phishing จากอีเมล แชท หรือเว็บโซเชียล ถ้าระบบรอให้ผู้ใช้เข้าเว็บแล้วค่อยเตือน อาจช้าเกินไป เพราะผู้ใช้อาจกรอกรหัสผ่านหรือ OTP ไปแล้ว

## แนวคิดหลัก

โปรเจคนี้ทำเป็น Chrome Extension ที่ตรวจลิงก์ตั้งแต่ก่อนผู้ใช้เข้าเว็บ โดยใช้ rule-based scoring ที่อธิบายเหตุผลได้ เช่น โดเมนคล้ายแบรนด์จริง, ไม่ใช้ HTTPS, URL ยาวผิดปกติ, มีคำว่า login/verify/OTP, ใช้ลิงก์ย่อ หรือฟอร์มส่งข้อมูลไปโดเมนอื่น

## ทำไมยังไม่ใช้ ML

เวอร์ชันนี้ตั้งใจทำเป็น AI-Lite / Explainable Rule-Based Engine ก่อน เพราะต้องการให้ระบบอธิบายได้ว่า “ทำไมถึงเสี่ยง” เหมาะกับการนำเสนอ concept และสามารถต่อยอดเป็น ML model ภายหลังได้

## Flow การทำงาน

```text
ผู้ใช้เปิดหน้าเว็บ
↓
Extension สแกนลิงก์ทั้งหมดในหน้า
↓
Analyzer ให้คะแนนความเสี่ยง 0–100
↓
ลิงก์เสี่ยงถูกไฮไลต์พร้อม badge
↓
ถ้าผู้ใช้คลิกลิงก์คะแนนสูง ระบบดักไว้ก่อน
↓
เปิดหน้า Warning แทนเว็บปลายทาง
↓
ผู้ใช้เลือกย้อนกลับ หรือเปิดต่อโดยยอมรับความเสี่ยง
```

## สิ่งที่ระบบตรวจได้

1. **HTTPS** — ถ้าเว็บ login ไม่ใช้ HTTPS จะเพิ่มคะแนนเสี่ยง
2. **URL ยาวผิดปกติ** — phishing มักทำ URL ยาวเพื่อซ่อนปลายทาง
3. **Subdomain ซ้อนหลายชั้น** — เช่น `login.paypal.com.evil-site.com`
4. **Brand impersonation** — เช่น `paypaI`, `kbank-login`, `scb-secure`
5. **Homoglyph / Punycode** — เช่น `xn--` หรือการใช้ตัวอักษรคล้ายกัน
6. **Suspicious keywords** — login, verify, account, OTP, password, token
7. **Redirect parameter** — เช่น `?redirect=https://evil.example`
8. **Shortener** — bit.ly, tinyurl, t.co
9. **Suspicious download** — exe, scr, bat, js, apk
10. **Form context** — มีช่อง password/OTP หรือ form action ส่งไปโดเมนอื่น
11. **Link text mismatch** — ข้อความลิงก์แสดง paypal.com แต่ href ไปเว็บอื่น

## ตัวอย่างผลลัพธ์

- `https://www.google.com/` ได้คะแนนต่ำ เพราะเป็น official domain และใช้ HTTPS
- `http://kbank-login-verify.top/account/update` ได้คะแนนสูง เพราะไม่ใช้ HTTPS, อ้างชื่อธนาคาร, มีคำว่า login/verify และใช้ TLD เสี่ยง
- `https://paypaI-security-login.example.com/verify/account?otp=true` ได้คะแนนสูง เพราะโดเมนคล้าย PayPal และมี OTP/account

## จุดเด่น

- ใช้งานจริงใน Browser ได้
- ตรวจลิงก์ก่อนคลิก ไม่ใช่แค่หลังเข้าเว็บ
- อธิบายเหตุผลการให้คะแนนได้
- ไม่ส่ง URL ออกนอกเครื่องในเดโม
- เหมาะสำหรับต่อยอดเป็น ML / API / Dashboard
- แสดงสัญลักษณ์สถานะเข้าใจง่าย: ✅ ปลอดภัย, ⚠️ น่าสงสัย, ⛔ เสี่ยงสูง

## ข้อจำกัด

- ยังไม่ใช่โมเดล ML ที่ train จาก dataset จริง
- ยังไม่เชื่อมฐานข้อมูลภัยคุกคาม เช่น Google Safe Browsing หรือ VirusTotal
- ยังไม่ตรวจอายุโดเมนจริง เพราะต้องใช้ WHOIS/RDAP API
- อาจมี false positive และ false negative

## แนวทางต่อยอด

1. เพิ่ม backend ด้วย FastAPI หรือ Node.js
2. เพิ่ม ML model เช่น Random Forest หรือ XGBoost จาก dataset phishing URL
3. เชื่อม Safe Browsing / VirusTotal API
4. เพิ่มฐานข้อมูล blacklist/whitelist
5. เพิ่ม dashboard สถิติ URL ที่ถูกบล็อก
6. ตรวจ screenshot หรือ DOM similarity กับหน้า login ของแบรนด์จริง
7. เพิ่มระบบ privacy เช่น hash URL ก่อนส่ง server

## ประโยคปิดนำเสนอ

โปรเจคนี้แสดงให้เห็นว่า แม้ยังไม่ใช้ ML model ก็สามารถสร้างระบบป้องกัน phishing เบื้องต้นที่ใช้งานจริงและอธิบายได้ โดยออกแบบให้ตรวจจับก่อนผู้ใช้กรอกข้อมูลสำคัญ และสามารถต่อยอดเป็นระบบ AI + Threat Intelligence ที่สมบูรณ์ในอนาคต

## คำอธิบายตอนเจอ false positive บน Google Search

ถ้าอาจารย์ถามว่าทำไมบางเว็บปกติอาจโดนเตือน ให้ตอบว่า:

> Rule-based system มีโอกาสเกิด false positive ได้ โดยเฉพาะหน้า Search Engine ที่มี redirect URL และ snippet ยาว เราจึงเพิ่ม Search Page Mode เพื่อวิเคราะห์ปลายทางจริง และแสดงเตือนเฉพาะลิงก์ที่มีความมั่นใจสูง วิธีนี้แสดงให้เห็นว่าระบบ security ต้องมีทั้ง detection และ false-positive reduction

## จุดเพิ่มสำหรับนำเสนอ: Simulator Lab

เปิดหน้า **เว็บจำลอง** เพื่อสาธิตให้เห็นชัดว่าระบบตรวจจับอะไรได้บ้าง เช่น:

- เว็บไม่ใช้ HTTPS และมีคำว่า login/verify/account
- โดเมนคล้ายแบรนด์ เช่น paypaI แทน paypal
- URL มี OTP/token ใน query string
- ลิงก์ย่อหรือ redirect ไปโดเมนอื่น
- Punycode / IDN ที่อาจหลอกตา
- ไฟล์ดาวน์โหลดน่าสงสัย เช่น `.exe`
- ฟอร์มที่มี password/OTP และส่งข้อมูลผ่าน HTTP หรือคนละโดเมน

ประโยคพูด: “ผมทำ Simulator Lab เพื่อให้อาจารย์เห็นผลของ rule-based engine โดยไม่ต้องเข้าเว็บ phishing จริง ระบบจะแสดงคะแนนและเหตุผลของแต่ละเคสแบบ explainable security”

## อัปเดต v1.1: ตรวจ SEO Spam / เว็บถูกฝังไฟล์แปลกปลอมในหน้าค้นหา

เพิ่มกฎสำหรับกรณีผลค้นหา Google/Brave ที่มีหัวข้อ adult/spam แต่ปลายทางเป็นโดเมนองค์กร/การศึกษา/เว็บทั่วไป เช่น path แบบ `wp-content`, `wpforms/tmp`, `wpcf7-files`, หรือไฟล์ PDF ที่ไม่สอดคล้องกับโดเมนจริง ระบบจะจัดเป็น “ลิงก์เสี่ยง/SEO spam” ไม่ได้สรุปว่าเป็น phishing เสมอไป แต่ควรเตือนผู้ใช้ก่อนกดเข้าเว็บ

## เพิ่มเติมสำหรับนำเสนอ v1.2: ขยายจาก Phishing เป็น Risky Content Filter

ประเด็นที่ใช้พูดกับอาจารย์:

> เวอร์ชันแรกของระบบเน้นตรวจ Phishing เป็นหลัก เช่น ลิงก์ปลอม หน้า Login ปลอม และการขอ OTP แต่จากการทดสอบจริงบนหน้าค้นหา พบว่าลิงก์เสี่ยงบางประเภทไม่ได้เป็น Phishing โดยตรง เช่น SEO spam, เว็บถูกแฮกฝัง PDF แปลก ๆ, ไฟล์ดาวน์โหลดเสี่ยง, เว็บพนัน หรือเว็บหลอกลงทุน ดังนั้นจึงขยายระบบเป็น Risky Content Filter ที่ยังคงใช้ Rule-Based AI และอธิบายเหตุผลได้ทุกข้อ

กลุ่มความเสี่ยงที่เพิ่ม:

1. Malware / ไฟล์เสี่ยง
2. Scam / Fraud เช่น ลงทุนกำไรสูง กู้เงินด่วน airdrop ปลอม
3. Gambling content เช่น สล็อต คาสิโนออนไลน์ เครดิตฟรี
4. Adult SEO spam / PDF แปลกบนโดเมนองค์กรหรือการศึกษา
5. Fake update / หลอกกด allow notification

คำตอบถ้าอาจารย์ถามว่า “ตรวจเนื้อหาได้จริงไหม?”:

> ระบบตรวจจากสัญญาณใน URL, ข้อความลิงก์, บริบทผลค้นหา และข้อความในหน้าเว็บ ไม่ได้อ่านความหมายลึกแบบ ML หรือ LLM ดังนั้นจึงเป็นการตรวจจับระดับ rule-based เพื่อคัดกรองความเสี่ยงเบื้องต้น สามารถต่อยอดด้วย Machine Learning หรือ API ภัยคุกคามจริงได้ในระยะถัดไป
