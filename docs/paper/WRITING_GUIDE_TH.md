# คู่มือให้ผู้เขียนบทความ Phish Radar

เอกสารนี้เป็นแนวทางค้นหลักฐานและแบ่งงานให้เพื่อนเขียนบทความเอง ไม่ใช่บทความฉบับส่งอาจารย์ อ่านคู่กับ [โครงบทความ](ARTICLE_OUTLINE_TH.md) และเอกสารอ้างอิงในโฟลเดอร์นี้

ตรวจแผนที่ source เมื่อ 17 ตุลาคม 2569 (2026-10-17) การตรวจครั้งนี้อ่านไฟล์เท่านั้น ไม่ได้รันระบบ ทดสอบ API หรือทดลองโมเดลใหม่ จึงต้องเก็บหลักฐานจากรุ่นที่จะใช้ส่งจริงก่อนเติมส่วนผลการดำเนินงาน

## 1. ตกลงขอบเขตก่อนเริ่มเขียน

- ใช้ชื่อโครงงาน รายชื่อผู้จัดทำ สาขา อาจารย์ และรูปแบบหน้ากระดาษตามที่อาจารย์กำหนด ห้ามเดาข้อมูลผู้จัดทำ
- เลือก commit และ model artifact ชุดเดียวเป็นฐานของบทความ บันทึก commit, model SHA-256, model version, feature schema, policy และวันที่เก็บผลไว้ด้วยกัน
- เนื้อหาหลักครอบคลุมระบบประเมินความเสี่ยง URL ผ่าน Web และ Chrome Extension พร้อมคำอธิบายและประวัติการตรวจ ส่วนระบบสมาชิก QR และการกรองโฆษณาอธิบายเป็นความสามารถประกอบตามพื้นที่บทความ
- หากจะประเมินการกรองโฆษณา ให้กำหนดวิธีทดลองแยกจากโมเดล URL การซ่อนองค์ประกอบหน้าเว็บไม่ใช่หลักฐานว่า Random Forest ตรวจ phishing ดีขึ้น
- คะแนนต่ำหรือ `allow` หมายถึงผลการประเมินตามข้อมูลและเกณฑ์ของระบบ ไม่ใช่ใบรับรองว่าเว็บไซต์ปลอดภัย

### ลำดับการทำงานที่ควรวาดเป็นภาพ

**Web แบบปกติ:** ผู้ใช้ใส่ URL → normalize และ local URL rules → `POST /predict` → backend สกัด feature ตาม bundle → RF probability → calibration → สูตรที่ bundle กำหนด → score/decision/model metadata → Web แสดงคะแนน → บันทึกประวัติ → ขอคำอธิบายผ่าน `POST /explain`

แสดงลูกศรของคำอธิบายแยกจากเส้นทางคำนวณคะแนน ในโหมด `ml_only` ที่ source รองรับ คะแนนมาจาก RF หลัง calibration ส่วน local rules เป็นหลักฐานประกอบคำอธิบาย Fuzzy และ consensus guardrail ไม่ถูกนำมารวมคะแนนในโหมดนี้ ต้องยืนยันว่ารุ่นที่จะรายงานใช้ `fusion_method=ml_only` จริง

**Extension:** service worker ตรวจ navigation หรือรับคำขอจาก content/popup → วิเคราะห์กฎ → อ่าน settings/privacy/ข้อยกเว้น → เรียก backend เมื่อเปิดใช้งาน → อ่านผลคะแนนและ policy → แสดง badge/หน้าเตือนตามเงื่อนไข ส่วน content script ตรวจลิงก์และบริบทบนหน้าเว็บเพิ่มเติม

อย่าเขียนว่าระบบรับประกันหยุดทุก request ก่อนเข้าถึงเว็บไซต์ปลายทาง การมี `onBeforeNavigate` และการเปลี่ยนแท็บไปหน้าเตือนเพียงอย่างเดียวไม่พิสูจน์การรับประกันนั้น ต้องเก็บ network timing แยกหากต้องการอ้างพฤติกรรมระดับนี้

**Privacy Mode:** ตรวจ local rules และแสดงว่าเป็นผลในเครื่อง ไม่เรียกผล RF ว่าเป็นผลที่ได้ในรอบนั้น ตรวจ source และ network ของแต่ละ client ก่อนอ้างรายละเอียดการไม่ส่งข้อมูลออก

**Backend ไม่มีโมเดล:** source มีเส้นทาง `model_unavailable_fuzzy_evidence` ส่วน client อาจมี fallback เมื่อ API ใช้งานไม่ได้ แยกสองกรณีนี้ในตารางทดสอบและอย่านำคะแนน fallback ปนกับผล RF

## 3. วิธีเขียนทั้ง 7 ส่วนตามภาพโจทย์

| ส่วน | สิ่งที่ผู้เขียนต้องตอบ | หลักฐานที่ต้องมี |
| --- | --- | --- |
| บทคัดย่อ | ปัญหา วัตถุประสงค์ วิธีพัฒนา วิธีประเมิน ผลสำคัญและข้อจำกัด | เขียนหลังได้ผลจริง ใช้ตัวเลขเดียวกับส่วนผล ไม่เติมคำว่าแม่นยำสูงโดยไม่มีการวัด |
| 1. บทนำ | ปัญหาที่ต้องการแก้ ผู้ใช้เป้าหมาย เหตุผลที่พัฒนา วัตถุประสงค์และขอบเขต | แหล่งอ้างอิงสถานการณ์และขอบเขตระบบที่พัฒนาจริง ห้ามใส่สถิติภัยคุกคามที่ไม่มีแหล่งและปี |
| 2. ทฤษฎีและงานวิจัยที่เกี่ยวข้อง | phishing, URL features, RF, calibration, metrics และงานที่ใช้เปรียบเทียบ | อ่านต้นฉบับ ระบุว่าแต่ละงานสนับสนุนการตัดสินใจใดของโครงงาน แยกวิธีของงานเดิมจากสิ่งที่เราเพิ่ม |
| 3. วิธีการดำเนินงาน | architecture, request flow, dataset/provenance, split, feature, สูตร, policy, LLM และวิธีประเมิน | source map, metadata ของ artifact และ protocol ทดลองที่ทำซ้ำได้ เขียนอ้างอิงพร้อมกับส่วนนี้ |
| 4. ผลการดำเนินงาน | ระบบที่พัฒนาได้ ผลทดสอบฟังก์ชัน ผลโมเดล และตัวอย่างการแสดงผล | ตาราง test case พร้อมผลจริง รูปที่มีคำบรรยาย ผลประเมินที่ผูกกับ model hash และ split |
| 5. สรุปและอภิปรายผล | วัตถุประสงค์ข้อใดทำได้ ผลมีความหมายอย่างไร ข้อจำกัดและข้อเสนอแนะ | ใช้ผลในส่วน 4 รองรับ ห้ามสรุปเกิน dataset/เงื่อนไขที่ตรวจ ถ้ามีกิตติกรรมประกาศให้ใส่ตามรูปแบบอาจารย์ |
| เอกสารอ้างอิง | แหล่งที่ใช้อ้างในเนื้อหาทั้งหมด | รายการตรงกับ citation ในเนื้อหา ใช้รูปแบบเดียวกันทั้งเล่ม ตรวจผู้แต่ง ปี ชื่อเรื่อง DOI/URL |

ให้ถามอาจารย์หรือดู template ของรายวิชาสำหรับจำนวนหน้า ขนาดอักษร จำนวนคอลัมน์ รูปแบบ citation และตำแหน่งกิตติกรรมประกาศ ภาพโจทย์ระบุหัวข้อ แต่ไม่ได้ยืนยันรายละเอียดรูปเล่มเหล่านี้

### ทำเอกสารอ้างอิงพร้อมรายการที่ 3 ในภาพ

รายการที่ 3 ในภาพคือหัวข้อ 2 ทฤษฎีและงานวิจัยที่เกี่ยวข้อง ให้ทำบรรณานุกรมควบคู่กัน และเพิ่มอ้างอิงต่อเมื่อเขียนวิธีดำเนินงานด้วย

1. ระหว่างเขียนทฤษฎีและงานวิจัยที่เกี่ยวข้อง จดทุกข้อความที่ยืมแนวคิด เช่น RF, probability calibration และวิธีประเมิน class imbalance
2. เปิดบทความต้นฉบับหรือเอกสารทางการที่รองรับข้อความนั้นจริง บันทึกผู้แต่ง ปี ชื่อเรื่อง เลขหน้า/หัวข้อ DOI/URL และวันที่เข้าถึงเมื่อรูปแบบกำหนด
3. ใส่ citation ในตำแหน่งที่ใช้แนวคิดทันที แล้วเพิ่มรายการท้ายบทความด้วยรหัสเดียวกัน
4. แยกแถวบันทึกเป็น “แนวคิดจากเอกสาร” กับ “การเลือกของโครงงาน” เช่น threshold Warning 60 / Block 80 ไม่ใช่ค่าที่บทความ RF รับรอง
5. ข้อความเกี่ยวกับ implementation ให้โยงกับไฟล์และ commit ของโครงงาน ส่วนผลประเมินให้โยงกับ artifact/report ของการทดลอง ไม่ใช้ paper ภายนอกแทนหลักฐานผลของเรา
6. ก่อนส่ง ตรวจสองทาง: ทุก citation มีรายการท้ายบทความ และทุกรายการท้ายบทความถูกอ้างในเนื้อหาจริง

ใช้ [REFERENCES_TH.md](REFERENCES_TH.md) ในชุดนี้เป็นจุดเริ่มค้นเอกสาร และเปิดตรวจต้นฉบับก่อนนำไปอ้าง เอกสารเดิม `docs/RESEARCH_REFERENCES_TH.md` ยังอธิบาย artifact รุ่นก่อน จึงไม่ใช่หลักฐานยืนยัน model identity ปัจจุบัน

## 5. หลักฐานที่เพื่อนต้องเก็บเพิ่มก่อนเขียนผล

### หลักฐานของรุ่นที่ใช้ทดลอง

เก็บในที่ที่ทีมตกลงร่วมกัน โดยไม่ commit ข้อมูลส่วนบุคคล token หรือ URL ที่มีค่าลับ

- commit SHA, วันเวลาและ timezone ของการทดสอบ, browser/Extension version, OS, Python/Node และ dependency รุ่นสำคัญ
- model SHA-256, `model_version`, `feature_schema_version`, `fusion_method`, `probability_method`, thresholds และ `production_ready`
- ผล `/health` และตัวอย่าง `/predict`/`/explain` ที่ปกปิดข้อมูลลับแล้ว ต้องแสดงแยกได้ว่าโมเดลพร้อม, LLM จริง, cache hit หรือ fallback
- dataset version/manifest, แหล่งที่มา, label, จำนวนก่อนและหลังทำความสะอาด, เงื่อนไข deduplicate และการแบ่ง train/calibration/validation/test
- แยกวันเผยแพร่แหล่งข้อมูล ช่วงวันที่ตัวอย่างถูกสังเกต วันดาวน์โหลด และวันรายงาน ห้ามใช้ปีของบริการแทนช่วงเวลาของ dataset

### ภาพประกอบที่ควรสร้างและตรวจ

### ตารางทดสอบที่ต้องบันทึกผลจริง

- Web และ Extension: URL ปกติ/น่าสงสัย/คะแนนสูง, ข้อมูลไม่ถูกต้อง, API timeout และ backend ใช้งานไม่ได้
- จุดขอบ policy: 59 / 60 / 79 / 80 และค่าก่อนปัดเศษที่ใกล้ threshold ตรวจผลจาก backend และการแสดงในทั้งสอง client
- แยกกรณีโมเดลไม่มีไฟล์, โมเดลโหลดไม่ได้ และ request ล้มเหลว ห้ามเหมารวมเป็น “โมเดลพร้อม” เพราะ `/health` ของรอบอื่นตอบได้
- Privacy Mode: สถานะ local-only, การปกปิด URL และ network requests ที่เกี่ยวข้องของ client แต่ละตัว
- LLM: provider/model ที่ตั้งค่าจริง, คำอธิบายสอดคล้องกับ score/decision, ข้อมูลลับถูกปกปิด, cold request/cache hit และ fallback
- บัญชี/ประวัติ/feedback: สมัคร เข้าระบบ ออกจากระบบ สิทธิ์ user/admin และการอ่านประวัติตามบัญชี โดยใช้บัญชีทดสอบ
- QR และการกรองโฆษณา: ประเมินเฉพาะเมื่อเลือกเป็นขอบเขตการทดลอง และรายงานแยกจากผล RF

แต่ละแถวควรมี test ID, เงื่อนไขตั้งต้น, input, expected result, actual result, pass/fail, หลักฐานและ commit ไม่ใช้แค่คำว่า “ทดสอบแล้วผ่าน”

### ผลโมเดลและข้อจำกัด

- รายงานอย่างน้อย confusion matrix, จำนวนตัวอย่างแต่ละ class, Precision, Recall, F1 และ FPR พร้อม threshold ถ้ามี PR-AUC/ROC-AUC ให้ระบุวิธีคำนวณ
- ถ้าจะเปรียบเทียบโมเดล ใช้ชุดทดสอบและ protocol เดียวกัน แสดง Recall และ FPR คู่กัน การลด FPR ด้วยการลด Recall ไม่ใช่ข้อสรุปว่า accuracy ดีขึ้นโดยอัตโนมัติ
- ระบุว่า split แยก URL, hostname หรือ registrable domain และแยกเวลาหรือไม่ อย่าใช้คำว่า domain-disjoint หากตรวจเพียง hostname
- ความน่าจะเป็นหลัง calibration และคะแนน 0–100 ไม่ใช่หลักฐานเพียงพอว่า calibration ดี ต้องมีผลประเมินที่รองรับถ้าจะอ้างคุณภาพนี้
- ไม่รวมตัวอย่างที่ใช้ปรับโมเดลหรือเลือก threshold เป็นผลทดสอบอิสระโดยไม่เปิดเผยการใช้ซ้ำ
- `REFERENCE_ROOT_FP_REPAIR_20261008_TH.md` ระบุว่ายังไม่มี forward-temporal test ครบ benign/phishing, ประวัติ baseline บางส่วนตรวจย้อนหลังไม่ได้ และ production/statistical gates ยังไม่ผ่าน ข้อจำกัดนี้ต้องคงไว้หากใช้ผลจากรอบดังกล่าว
- อย่าเติมตัวเลขผลทดลองจากการคาดประมาณ หากยังไม่มีหลักฐานให้ใส่รายการงานที่ต้องทำในเอกสารทำงาน และเว้นผลออกจากบทความฉบับส่งจนกว่าจะวัดจริง
