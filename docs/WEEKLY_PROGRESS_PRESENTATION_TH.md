# บทพูดรายงานความคืบหน้าประจำสัปดาห์

หัวข้อ: **Phish Radar AI — จากตัวตรวจลิงก์สู่ระบบที่มีโมเดล สมาชิก และประวัติที่ตรวจสอบได้**

รูปแบบนี้ออกแบบสำหรับการพูดประมาณ **5–7 นาที** ต่อหน้าอาจารย์ โดยเน้นงานที่ทำเสร็จและหลักฐานจากระบบจริง ไม่ลงรายละเอียดโค้ดมากเกินไป

## บทพูดแบบพร้อมใช้

### 1. เปิดการนำเสนอ — สิ่งที่เปลี่ยนในสัปดาห์นี้

> สวัสดีครับ สัปดาห์นี้ผมพัฒนา Phish Radar AI จากเดิมที่เน้นการตรวจ URL และแสดงคำเตือน ให้กลายเป็นระบบที่เชื่อมต่อกันมากขึ้นทั้ง Extension, Web App, Backend และ MySQL/MariaDB  
> งานหลักที่ทำเสร็จมี 5 ส่วน คือปรับวิธีคำนวณความเสี่ยงให้มีหลักฐานรองรับ เพิ่มระบบสมัครและ Login เพิ่มประวัติการค้นหาที่ผูกกับผู้ใช้ เปลี่ยนขั้นตอนเปิดระบบประจำวันมาใช้ Git Bash และกำหนด Qwen เป็น LLM ค่าเริ่มต้นสำหรับการอธิบายผลแบบ Local

**ชี้ภาพ:** Popup ของ Extension หลังตรวจ URL หนึ่งรายการ ให้เห็นคะแนน สถานะ และเหตุผลสำคัญ

### 2. ระบบเชื่อมต่อเป็น 3 ชั้น

> ตอนนี้ระบบแบ่งเป็น 3 ชั้นครับ  
> ชั้นแรกคือ Browser ซึ่งมี Chrome Extension และ Web App ทำหน้าที่รับ URL และแสดงผล  
> ชั้นที่สองคือ FastAPI Backend ซึ่งคำนวณ URL RiskScore ด้วย L1 Logistic Regression กำหนด decision policy และส่งหลักฐานให้ Qwen อธิบาย  
> ชั้นที่สามคือ MySQL/MariaDB สำหรับเก็บผู้ใช้ อุปกรณ์ Session และประวัติการตรวจ  
> การแยกแบบนี้ทำให้แก้หรือทดสอบแต่ละส่วนได้โดยไม่ต้องผูกทุกอย่างไว้ใน Extension เพียงไฟล์เดียว

**ชี้ภาพ:** แผนภาพ `Browser → Backend → MySQL/MariaDB` จากสไลด์ 3

### 3. คะแนนความเสี่ยงไม่ได้เลือกจากความรู้สึก

> ส่วนของคะแนนความเสี่ยง ผมเพิ่มชุดข้อมูลรวม 10,000 URL แบ่งเป็น phishing 5,000 และ legitimate 5,000  
> ข้อมูล phishing มาจาก PhishTank, OpenPhish และ seed ของโปรเจกต์ ส่วนข้อมูล legitimate ใช้ Tranco และ seed ของโปรเจกต์  
> ในการประเมินใช้ Stratified Group Cross-validation จำนวน 5 folds โดยแบ่งกลุ่มตาม hostname เพื่อไม่ให้ URL จากโดเมนเดียวกันหลุดไปอยู่ทั้งชุดฝึกและชุดทดสอบ  
> โมเดลคำนวณ probability ด้วย Logistic sigmoid โดยตรงและใช้ L1 regularization เลือกค่า C จาก log loss, Brier score และ ROC-AUC จากนั้นเลือก warn/block threshold ภายใต้เพดาน FPR พร้อม Wilson confidence bound 95 เปอร์เซ็นต์

**ชี้ภาพ:** Pipeline `10,000 URL → grouped holdout → 5-fold Grouped CV → L1 Logistic → FPR policy`

**ประโยคกันการอ้างเกินจริง:**

> ผลนี้เป็นผล Cross-validation บนชุดข้อมูลรอบปัจจุบัน ยังไม่ใช่การรับรองประสิทธิภาพใน Production และขั้นต่อไปยังต้องมีชุดทดสอบแบบ time-split ที่ไม่ถูกใช้เลือกค่า policy

### 4. RiskScore เรียนจากข้อมูลและมี threshold สองระดับ

> สูตรที่ใช้งานคือ FinalScore เท่ากับ 0.40 คูณ RuleScore บวก 0.60 คูณ MLScore โดย MLScore มาจาก probability ของ Logistic Regression
> Development OOF เลือก warn threshold ที่ 0.35 ได้ Precision 99.25 เปอร์เซ็นต์, Recall 96.15 เปอร์เซ็นต์, F1 97.68 เปอร์เซ็นต์ และ FPR 0.67 เปอร์เซ็นต์
> Independent grouped holdout ได้ FinalScore ROC-AUC 99.19 เปอร์เซ็นต์, PR-AUC 99.30 เปอร์เซ็นต์ และ warn FPR 1.12 เปอร์เซ็นต์ ซึ่งสูงกว่าเป้าหมาย 1 เปอร์เซ็นต์เล็กน้อย จึงรายงานข้อจำกัดตามจริง
> Block threshold อยู่ที่ 0.8006 เพราะ policy สำหรับ block ใช้เพดาน FPR ที่เข้มกว่า warn ระบบจึงเน้น warn ก่อนและ block เฉพาะผลที่มั่นใจมากที่สุด

**ชี้ภาพ:** ตาราง development เทียบ holdout พร้อม ROC-AUC, Recall, F1 และ FPR

**หากอาจารย์ถามว่าทำไม block threshold สูงถึง 100:**

> เพราะการ block ผิดมีต้นทุนต่อผู้ใช้สูง ผมจึงใช้เพดาน FPR ที่เข้มกว่า warn และตรวจด้วย Wilson upper bound หากข้อมูลยังไม่พอ ระบบจะเลือกเตือนแทนการ block เพื่อไม่อ้างความมั่นใจเกินหลักฐาน

### 5. ระบบสมาชิกเก็บเฉพาะข้อมูลที่จำเป็น

> ส่วนถัดมาคือระบบสมาชิก ตอนนี้ผู้ใช้ทั่วไปและ Admin สมัครและ Login จากหน้าเดียวกันได้ โดยบัญชีใหม่จะเริ่มเป็น User เสมอ ส่วน Admin ต้องเลื่อนสิทธิ์จากฐานข้อมูล  
> ใน MySQL/MariaDB เก็บ Username, Email, Role และ PasswordHash ที่สร้างด้วย Argon2id ไม่ได้เก็บรหัสผ่านจริง  
> หลัง Login ระบบสร้าง Device และ Session โดยเก็บเฉพาะ hash ของ token ส่วน Browser รับ Session ผ่านคุกกี้ HttpOnly เพื่อลดความเสี่ยงที่ JavaScript จะอ่าน token โดยตรง

**ชี้ภาพ:** หน้า Login/Register ที่แสดงสถานะ Backend พร้อมใช้งาน ไม่ต้องพิมพ์รหัสผ่านจริงลงในภาพ

### 6. ประวัติการค้นหาผูกกับ User และ Device

> เมื่อผู้ใช้ตรวจ URL ระบบจะบันทึกประวัติลงตาราง SearchHistory โดยผูกกับ User และอุปกรณ์ที่ Login อยู่  
> ข้อมูลที่เก็บประกอบด้วย URL ที่ตัด credentials, query string และ fragment ออกแล้ว, hash สำหรับเชื่อมโยงรายการ, Rule evidence, RiskProbability, RiskScore, decision, warn/block threshold, เวอร์ชันโมเดลและเวลา  
> ค่าเริ่มต้นเก็บย้อนหลัง 90 วัน และถ้าเปิด Privacy Mode ประวัติจะอยู่ใน Browser โดยไม่ส่ง URL ไป Backend

**ชี้ภาพสองส่วน:**

1. Dashboard ที่มีประวัติอย่างน้อย 3 รายการและคะแนนต่างกัน
2. phpMyAdmin ที่ Query ตาราง `SearchHistory` ให้เห็น `UserId`, `UserDeviceId`, คะแนน และ `CreatedAt`

ควรใช้ข้อมูลทดสอบและปิดบัง Email, token hash หรือ URL ที่เป็นข้อมูลส่วนตัวก่อนนำเสนอ

### 7. Workflow ประจำวันเปลี่ยนมาใช้ Git Bash

> เพื่อให้เปิดระบบง่ายขึ้น งานประจำวันเปลี่ยนมาใช้ Git Bash ครับ  
> คำสั่ง `./start-demo.sh` เปิดทั้ง Backend และ Web App, ส่วน `./migrate-db.sh` ใช้สร้างตารางบน MySQL/MariaDB  
> PowerShell ยังใช้เฉพาะงานที่เหมาะกับ Windows เช่นตั้งค่า hosts และรัน validation ไม่ได้ถูกนำมาใช้เป็นคำสั่งหลักในการเปิดเดโมแล้ว

**ชี้ภาพ:** Git Bash ที่แสดงข้อความ `Backend: http://127.0.0.1:8765` และ `Web App: ...:5505` โดยไม่มี error

### 8. Qwen เป็นค่าเริ่มต้น แต่ไม่ได้เป็นผู้ตัดสินคะแนน

> สำหรับ LLM ผมเลือก Qwen3:4b ผ่าน Ollama เป็นค่าเริ่มต้น เพราะรันในเครื่องได้ ไม่ต้องส่ง URL ไปผู้ให้บริการภายนอก และไม่มีค่า API สำหรับการทดลอง  
> บทบาทของ LLM คือแปลง RiskScore, decision และหลักฐานหลายชั้นให้อ่านง่ายขึ้นเท่านั้น ไม่ได้แก้คะแนน ไม่ได้กำหนด decision และระบบยังตรวจต่อได้หาก LLM ไม่พร้อม  
> ส่วน OpenAI Cloud เก็บไว้เป็นตัวเลือกสำหรับ Benchmark ภายหลัง โดยจะใช้ URL และ Prompt ชุดเดียวกัน เปรียบเทียบความถูกต้องของคำอธิบาย, JSON pass rate, hallucination, latency และต้นทุน ก่อนสรุปว่าโมเดลใดเหมาะกว่า

**ชี้ภาพ:** สถานะ `Ollama · qwen3:4b พร้อมใช้งาน` คู่กับตัวอย่างคำอธิบายภาษาไทยหนึ่งรายการ

### 9. ปิดการนำเสนอ — สิ่งที่ได้และขั้นต่อไป

> สรุปสัปดาห์นี้ ระบบไม่ได้เพิ่มเฉพาะหน้าจอ แต่เพิ่มส่วนที่ตรวจสอบย้อนกลับได้ตั้งแต่ที่มาของข้อมูล สูตร FinalScore แบบ Rule 40 เปอร์เซ็นต์และ ML 60 เปอร์เซ็นต์ วิธีเลือก warn/block threshold ไปจนถึงผู้ใช้ Session และประวัติในฐานข้อมูล
> ขั้นต่อไปมี 3 เรื่องหลัก คือหนึ่ง เพิ่ม time-split holdout เพื่อทดสอบกับข้อมูลคนละช่วงเวลา สองทำ LLM benchmark ด้วยชุดทดสอบอย่างน้อย 30 กรณี และสามเพิ่ม Admin API กับ audit log เพื่อลดการจัดการสิทธิ์ผ่าน SQL โดยตรง  
> เป้าหมายคือทำให้ระบบพร้อมสำหรับการทดลองกับข้อมูลจริงที่ได้รับอนุญาต โดยยังควบคุม False Positive และความเป็นส่วนตัวของผู้ใช้ครับ

## ภาพที่ควรเตรียมก่อนนำเสนอ

### ภาพที่ต้องมี

1. **Extension Popup หลังตรวจ URL** — ให้เห็น URL, คะแนน, สถานะและเหตุผล
2. **ตาราง/กราฟ Risk Model** — ใช้ผล development และ independent holdout จากรายงานจริง
3. **หน้า Login/Register** — ต้องไม่มีข้อความ `Failed to fetch`
4. **Dashboard Search History** — มีข้อมูลทดสอบหลายระดับคะแนน
5. **phpMyAdmin SearchHistory** — แสดงว่าข้อมูลผูกกับ User/Device จริง
6. **Git Bash เปิดระบบสำเร็จ** — ไม่มี error และเห็น URL ของ Backend/Web App
7. **Qwen พร้อมใช้งาน** — แสดงชื่อโมเดลและคำอธิบายหนึ่งตัวอย่าง

### ภาพที่ใช้เป็นสไลด์สำรอง

- phpMyAdmin ที่เห็น `Users`, `UserDevices`, `Sessions`, `SearchHistory`
- ผล `/health` ที่แสดง Database, model และ LLM พร้อม
- หน้า Warning ที่แยก Rule evidence, URL Risk Model, decision policy และ LLM
- ตารางแหล่งข้อมูลและเอกสารอ้างอิง

### ภาพที่ไม่ควรใช้เป็นหลักฐาน

- ภาพแชทที่เป็นรายการสั่งงาน ใช้เป็น checklist ส่วนตัวได้แต่ไม่แสดงความสำเร็จของระบบ
- Terminal ที่มี error หรือ path ส่วนตัวจำนวนมาก
- หน้าที่มี password, session token, API key หรือข้อมูลผู้ใช้จริง
- ภาพ UI หลายภาพย่อเล็กในหน้าเดียวจนอ่านข้อความไม่ได้

## คำถามที่อาจถูกถาม

### ทำไมใช้ข้อมูลสมดุล 5,000 ต่อ 5,000?

> ใช้เพื่อควบคุมการทดลองและเปรียบเทียบโมเดลในรอบแรก แต่สัดส่วนการใช้งานจริงจะไม่สมดุล จึงต้องเพิ่ม time-split holdout และประเมิน Precision/Recall/FPR บน traffic ที่ใกล้สถานการณ์จริง

### ทำไมไม่ให้ LLM ตัดสินว่าเป็น phishing?

> เพราะคำตอบของ LLM อาจเปลี่ยนตาม prompt หรือรุ่นโมเดล ระบบจึงให้ URL Risk Model และ FPR policy เป็นผู้กำหนดคะแนน/decision ส่วน LLM ทำหน้าที่อธิบายเพื่อให้ผลตรวจทำซ้ำและตรวจสอบได้

### เก็บรหัสผ่านหรือ URL เต็มหรือไม่?

> รหัสผ่านเก็บเฉพาะ Argon2id hash ส่วนประวัติ URL ตัด credentials, query string และ fragment ออกก่อนบันทึก พร้อมมี Privacy Mode สำหรับเก็บประวัติใน Browser เท่านั้น

### ผล 96–98 เปอร์เซ็นต์เชื่อถือได้แค่ไหน?

> เป็นผลจาก grouped cross-validation บน snapshot ปัจจุบัน ช่วยลด hostname leakage แต่ยังต้องยืนยันด้วยข้อมูลคนละช่วงเวลาและข้อมูลการใช้งานจริงที่ได้รับอนุญาตก่อนสรุปประสิทธิภาพระดับ Production
